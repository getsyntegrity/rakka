## 3. Findings

**F-1 (high) GOV-15: provenance of the "Owner decision" is thin and the decision does not unblock anything it appears to.** The decision exists only as an Architect edit of the issue body (`Owner decided option (b) of this proposal on 2026-10-25`, #1065 body "Owner decision recorded on 2026-10-25"). No verbatim Owner words, no comment, no ADR. Compare ADR 0031 and ADR 0030, which quote the Owner literally and name the commit. The body itself says it "decides the scope only", accepts no ADR amendment, "does not settle the lock-order design, and does not make #785 ready". Labels unchanged (`prio:P1`, `status:ready`). The body also leaves AC-R5-1 ("Owner decision field reads `pending`") superseded rather than edited. Taxonomy: 1 Accepted for scope; amendments to ADR 0010 :162/:170, ADR 0015 :158 and the `ErrInvalidHandle` text, ADR 0024 D2 item 2 (`0024:139`) = 4 Not designed; lock order = 4; evidence = D13, oracle applicability pending determination. Correction: add the Owner's verbatim words (and the session) to #1065, as ADR 0031 does; keep scope-only wording.

**F-3 (high) GOV-15 follow-ups have no owner story.** Decision (b) requires three artifacts before #785 can start: ADR amendments (ADR 0010, 0015, 0024), a lock-order design, and a resolution design ("the lookup has to go to the System that owns the handle": `watch.go:117-122`, `registry.go:23-35`; `register` delivers an immediate `Terminated` for a missing record, `watch.go:161-181`). I searched all GOV titles: only #1188 (GOV-42, ADR 0014 D2) and #1195 (GOV-48, identity rule) are adjacent; none proposes the 0010/0015/0024 amendments or the lock-order design. #785 and #827 stay `status:blocked` with their blocker described as "accepted ADR amendment" (#827 dependency row) which nobody is scheduled to produce. Also Pekko checks: `DeathWatch.scala:35-49` accepts any `InternalActorRef` (confirmed); no Pekko spec watches across two systems (`DeathWatchSpec` has no second ActorSystem; `ActorSystemSpec.scala:213-273` second systems are used for termination callbacks only), so whether an applicable oracle exists is pending determination under ADR 0033 D13 (Pekko code `DeathWatch.scala:35-49` accepts any `InternalActorRef`; one run is recorded in ADR 0017:493). Related Pekko evidence the proposal and design should also cite: typed `ActorRefResolver.scala:66-75` throws `IllegalArgumentException` when a ref from another ActorSystem is serialized through this system's resolver. Correction: create a story (or extend #1188-style) for "ADR amendment set for cross-System watch" and one for the lock-order design; list them as `depends_on` of #785.

**F-2 (high, Pekko-source contradiction) GOV-06 and GOV-14 claim FSM depends on ReceiveTimeout; Pekko FSM does not use it.** GOV-06 Context: "`ReceiveTimeout` is needed by FSM" (plan C-19), R5: "FSM state timeouts and Typed `setReceiveTimeout` depend on the answer". GOV-14 R5: "FSM depends on keyed timers and on `ReceiveTimeout` (GOV-06)". `A/FSM.scala` contains zero occurrences of `ReceiveTimeout`/`setReceiveTimeout` (grep); state timeouts are `scheduler.scheduleOnce(d, self, TimeoutMarker(generation))` (`FSM.scala:898`, handled at `:814`, `TimeoutMarker` at `:102`; `setTimer` single mode `:145`). The FSM stories bear this out: #947 (FSM-04, state timeouts) has no dependency on #1037. Only Typed `setReceiveTimeout(timeout, msg)` (`actor-typed/.../scaladsl/ActorContext.scala:205-219`, TYP-16 #987, which does `depends_on` #1037) really depends on GOV-06. Correction: remove the FSM-to-ReceiveTimeout claim from GOV-06 Context/R5 and GOV-14 R5; FSM depends on the scheduler/timers (C-05/C-06, TIM) only.
