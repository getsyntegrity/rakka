## 5. Lock-order / deadlock analysis (read of all 33 non-test Go files of `pekko-actor`)

Method: grep for every `Lock()`, `sync.`, `chan`, `<-`, `atomic.` in non-test files; a crude script listing the calls made between each `Lock()` and its `Unlock()`; then reading every function that holds a lock. Not machine-checked (no `-race`, no lock-order tool run; this audit may not execute anything). The proof below is a proof by reading of develop 9abfb40.

### 5.2 Acquisition-order graph (every place a lock is acquired while another is held)

Only two nested acquisitions exist, both the same direction and both inside ONE System:
- E1 `System.mu -> cell.mu(c)`: `adjustCore` (`supervision_failure.go:63-65`) for the cell `c` of that System.
- E2 `System.mu -> cell.mu(new cell)`: `commit` (`hierarchy.go:143`) calls `i.inherit` (`hierarchy.go:159`), which locks the new, still unpublished cell (`supervision_failure.go:45`).
No edge `cell.mu -> System.mu` and no edge `cell.mu -> cell.mu` exists: every critical section under `cell.mu` calls only `*Locked` helpers (`takeOutgoingLocked`, `takeWatchersLocked`, `settleDeathsLocked`, `processDeathsLocked`, `admitDeathLocked`, `laneReadyLocked`, `holdLocked`, ... all pure state), and the functions that must reach another lock release first: `settleDeathsLocked` unlocks before `c.sys.publish` (`watch.go:278-282`); `acceptStop` unlocks before `leaveWatchees` (`stop.go:55-56`); `finalize` unlocks before `detach`, `publish`, `notifyWatchers` (`stop.go:111-117`). `System.mu` sections call `rec.id()`, `rec.identity()`, `rec.retirable()`, `assignID`, `markOrigin` which take no lock (`cell.go:91-96`). ADR 0024 I6 and `hierarchy.go:38-42` state the same order.
Rank order: System.mu (1) < cell.mu (2) < Hub.mu (3, leaf). Every nested acquisition goes up in rank and no two locks of the same rank are ever held together. A directed cycle would need a down-rank or same-rank edge. None exists. Safe by reading.

### 5.3 The cross-System paths (what option (b) adds), as sequences of single-lock sections

Existing same-System code already treats the subject as "a record of the cell's own System". Cross-System only changes WHICH System's registry/record is touched; each step below locks exactly one lock and releases it before the next:
- Watch A.a -> B.b: A.a.mu (`stopAccepted` `watch.go:156`) -> [B.mu via `lookupID` `registry.go:32`, once the owner lookup replaces `watch.go:122`] -> A.a.mu (`addRegistration` `:201`) -> B.b.mu (`addWatcher` `:357`) -> A.a.mu (re-check `:184`, `removeWatcher` B.b.mu `:370`). Never two held.
- Subject B.b finalizes: B.b.mu (`stop.go:104`) released -> B.mu (`detach`) -> `notifyWatchers` -> A.a.mu (`notifyTerminated` `watch.go:251`) released -> `A.exec.Execute`. Never two held.
- Watcher A.a stops: A.a.mu (`stop.go:44`) released -> [B.mu lookup, B.b.mu `removeWatcher`] sequentially (`leaveWatchees` `watch.go:407-413`).
- Mutual watch a<->b with `A.Terminate()` and `B.Terminate()` concurrently: each side's lock sections are the single-lock sections above; no thread holds a lock while waiting for another System's lock, so there is no hold-and-wait, hence no deadlock. Waiting structure: `Shutdown` waits only on its own System's root `done` (`system_shutdown.go:56-70`); no code waits on another System's `done`. Notifications are asynchronous (`Execute`). A mutual plain `Watch` produces a death-pact cascade (each side's `OnTerminated`-less actor stops), which terminates: `acceptStop` is idempotent (`stop.go:45`), a notification to a stopping/closed cell is discarded (`watch.go:253, 331`).
- Duplicate notification: exactly one of {finalize snapshot (`takeWatchersLocked` under the same `c.mu` that sets `closed`, `stop.go:104-110`), `addWatcher` returning false because `closed` (`watch.go:359`)} wins for a given registration; plus the generation check (`watch.go:253, 331`). Same-System argument holds unchanged cross-System.

### 5.4 Result

No lock-order cycle and no deadlock found, for the current code and for option (b) The conclusion holds while these properties of the current code hold (observation by reading, not a decision):
- I-X1: no lock of any System is held while calling any `record` or `watcherLink` method, `lookupID`, or `Execute` on an object that may belong to another System (all of `addWatcher`, `removeWatcher`, `notifyTerminated`, `lookupID`, `Execute` run with no lock held today; keep it so).
- I-X2: System.mu -> cell.mu stays within one System; never take `B.mu` while holding anything of A.
- I-X3: the cross-System lookup is `owner().lookupID(id)` then release, as in `registry.go:31-35`; do not hold `B.mu` across `addWatcher`.
- I-X4: IDs unique per process (`id.go:15`); the watcher keys `watching` (`cell.go:59`) and the subject keys `watchers` (`cell.go:60`) by ID, so a per-System ID sequence (ADR 0024 option D) would collide.
Caveat on the claim: it is a read-based proof for one commit, not a mechanical one. It does not cover user code (dead-letter subscribers run on the publisher's goroutine with no lock, `hub.go:60-69`; an inline executor test seam can re-enter, which is re-entrancy, not a lock cycle).

### 5.5 Design blockers that are NOT deadlocks (found while building the graph)

- B1 (concrete interleaving, F1): `Stop` of watcher A.a while it watches B.b. `acceptStop` takes `subjects := takeOutgoingLocked()` which is `[]ID` only (`watch.go:378-386`), and `leaveWatchees` resolves each ID in `c.sys` = A (`watch.go:409`). `A.lookupID(B.b's ID)` returns nil (IDs are process-unique, B's entries are only in `B.byID`), so `removeWatcher` is never called. B.b keeps `watchers[a] = watchEntry{w: A.a cell}` (`watch.go:365`) until B.b finalizes. If B.b is a guardian or any long-lived actor the retained link keeps A.a's cell, and through `cell.sys` the whole System A, reachable from B: exactly what DTH-02's user story says must not happen, and it repeats once per watcher cell that watches and dies (unbounded growth in B.b's map). Not a correctness bug for notifications (A.a is stopped, `watch.go:253` discards). Resolving `rec` through the owner in `resolve` (needed by DTH-01) fixes `Unwatch` (`watch.go:240-242`) and `register` but NOT the stop path; the registration must retain the owner/record (e.g. in `watchReg` or a `[]struct{owner,id}` instead of `[]ID`).
- B2: `Terminated.Who()` returns an `ID` only (`watch.go:22-25`); a consumer cannot tell which System the subject belonged to. The ID is unique per process so it is unambiguous, but there is no accessor to the owning System/Address. Not in any story's AC. Design question for DTH-03 (low).

## 6. Pekko DeathWatch semantics compared (source read; specs named)

- Watch is a system message to the subject (`DeathWatch.scala:40`), the subject adds the watcher in its own cell loop (`:182-197`); all mutation is single-threaded in the cell's system-message loop (`ActorCell.scala:513-543`, `:522` for `DeathWatchNotification`), and system messages are enqueued by CAS (`Mailbox.scala:476-488`), so Pekko has no lock-order question at all. Go does the registration synchronously with a direct call under the subject's `cell.mu` (`watch.go:357-367`): observable result equal, but a different mechanism, and cross-System it makes a thread of System A take B's cell lock briefly. Not a Pekko behaviour to port; a Go adaptation that needs the I-X invariants above.
- Cross-System in Pekko: no comparison of Systems anywhere; a Watch to an actor of a terminated System reaches `deadLetterMailbox` -> `DeadLetterActorRef.specialHandle` -> `DeathWatchNotification(existenceConfirmed=false)` to the watcher (`ActorRef.scala:693-698`). I did not find a spec that watches across two in-process ActorSystems. Nearest: `ActorSystemSpec.scala:213,235,264,273` use a second system for termination callbacks only; `AddressTerminatedTopicBenchSpec.scala:45` second system in a benchmark; remote specs `RemoteDeathWatchSpec.scala` (classic:79-101, artery:70-94) use remoting. No Pekko spec for the cross-System half was found. Pekko evidence available: code (`DeathWatch.scala:35-49`, `ActorRef.scala:693-698`) and the probe run recorded in accepted ADR 0017:493 (`watch`/`watchWith` on a reference of another System are not rejected and `Terminated` arrives; the run's artifact was not verified here). A missing dedicated spec does not show that no applicable oracle exists. Pending determination: (1) whether the code and the recorded run form an applicable oracle; (2) if so, whether a differential scenario against Pekko can be built and is sufficient (ADR 0033 D13); (3) only if the oracle is shown not to apply, with the reason documented, whether approval of alternative evidence comes into question.
- Terminated delivery: DWN processed -> `watching -= actor`, `self.tell(Terminated(...), actor)` (sender = watched), `terminatedQueuedFor` (`DeathWatch.scala:99-115`), guard `!isTerminating` (`:109`) matches Go `admitDeathLocked` stopping check (`watch.go:331`). Unwatch: `terminatedQueued -= a` (`:75`) = Go `delete(c.termEntry, subject)` (`watch.go:238`).
- Pekko identity: `ActorRef.equals` = path + uid (`ActorRef.scala:183-186`); Go: process-unique incarnation ID. No generation counter in Pekko.
- Pekko order at termination: `unwatchWatchedActors` at `terminate` (`FaultHandling.scala:185`) and again at finish (`:268`), `tellWatchersWeDied` at `:266`. Go: unwatch at `acceptStop` (`stop.go:54-56`), tell watchers in `finalize` (`stop.go:117`). ADR 0010:174 describes the withdrawal AFTER the notifications ("then the withdrawal of the actor's own registrations, then Done") but code withdraws at acceptance (`stop.go:36-41`): pre-existing documentation drift (F13).
- `Terminated` carries `existenceConfirmed`/`addressTerminated` (`Actor.scala:123-125`); Go has neither (ADR 0010:170 records that).

## Key Learnings

1. Option (b) is deadlock-safe by reading: the only nested acquisitions in `pekko-actor` are `System.mu -> cell.mu` within a single System (`supervision_failure.go:63-65`, `hierarchy.go:143/159`), and every cross-System call (`lookupID`, `addWatcher`, `removeWatcher`, `notifyTerminated`, `Execute`) already runs with no lock held.
2. The real cross-System defect is not a lock cycle but the stop path: `leaveWatchees` resolves subject IDs in the watcher's own registry (`watch.go:407-413`), so foreign subjects keep a stale watcher link and retain the watcher's cell and System.
3. Of the three ADR amendment proposals only ADR 0010 line 170 is strictly required by GOV-15 option (b); the ADR 0024 D2.2 sentence concerns `Done`, ADR 0024 line 268 already places cross-System Watch out of scope, and ADR 0015's `[Owner, R2]` rule still holds for Ask.
4. GOV-15 option (b) is an Owner scope agreement only; no ADR text is accepted and for the cross-System half no Pekko spec was found (evidence found is code plus the run recorded in ADR 0017:493); whether that is an applicable oracle, and whether a differential scenario is sufficient evidence under ADR 0033 D13, are pending determination.
5. DTH-04 and DTH-03 change statements that ADR 0010 already records as accepted (line 176 "no dead letters", line 170 "no existenceConfirmed flag"), and their ADR 0033 D5 impact lists do not name them.
