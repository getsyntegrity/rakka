## 4. Findings against the ADRs

- **ADR 0010, Amendment 2026-11-04, divergence 5a (lines 217-218, 223).** Pekko publishes `SuppressedDeadLetter(PoisonPill, sender, deadLetters)` in the three situations the amendment names: an actor already stopped (`DL1`, `DL1b`), a full bounded mailbox (`DL7`), and the mailbox clean-up of a stop that was accepted while a `PoisonPill` was still queued (`DL8`, `DL8c`). It never publishes a `DeadLetter` for the `PoisonPill` in those runs. In 9 of the 11 `DL8b` runs no event for the `PoisonPill` appears; *inferred* (no log line shows it): the actor consumed the `PoisonPill` in its own turn, which stopped it.
- **The recipient is `deadLetters`, not the dead actor, for every suppressed event** (`DL1` [006], `DL3` [005], `DL5` (a) [004], `DL7` [019]); for `DeadLetter` the recipient is the dead actor (`DL4` [004], `DL7` [010], `DL8` [011]). A goPekko `SuppressedDeadLetter` that carries the original recipient would differ from Pekko (S4, observed).
- **ADR 0032 D3 (absent sender) and D6 (dead letters keep the sender).** With no sender the event's sender is `deadLetters` in both event kinds (`DL1` [006], `DL4` [004], `DL8` [011]); with a sender the sender is kept (`DL1b` [004], `DL5` (a) [004]). This is the shape D3 deferred to #896 and D6 expects.
- **ADR 0032 D4 (`TellFrom`).** Both `DL1` and `DL1b` show the sender surviving the dead-letter path; nothing in these runs concerns the name of the send function.
- **`Kill` is not suppressed** (`DL4` [004]): ADR 0010's amendment is about `PoisonPill` only; `Kill` to a stopped actor is a plain `DeadLetter` (the order of several queued `Kill`/`PoisonPill` dead letters at stop, item 5c of the amendment, was not run).
- **`Terminated` is suppressed** (`DL3` [005]); this is the same marker mechanism.
- **ADR 0038 D7.** `DeadLetter`, `SuppressedDeadLetter` and `AllDeadLetters` are three distinct channels: a `SuppressedDeadLetter` reaches `sd` and `all` and not `dl`; a `DeadLetter` reaches `dl` and `all` and not `sd` (every scenario above). The default listener does not subscribe to `SuppressedDeadLetter` (S7), and a `DeadLetter` whose message wraps a suppressed payload is skipped by the listener (`DL6`), although it is a `DeadLetter` event for any other subscriber (`DL6` [005]).

## 5. Differences from the inferred expectations

Every expectation of the Owner's earlier analysis (section 3, "Inferred" column) was observed as inferred in `DL1` to `DL8c` except the race in `DL8b`, with two qualifications that are not mismatches of the expectation but of the harness design, stated plainly:

1. **`DL8` as first designed did not exercise the mailbox clean-up.** The first build of the scenario stopped the actor with `ActorSystem.stop` (S9: a `StopChild` message to the guardian, asynchronous). That run was reported by the Dev; its raw log was not kept (overwritten), so it is not evidence here. *Reported:* the actor handled `m2`, `PoisonPill` produced no event, and a `SuppressedDeadLetter(Terminate() ...)` appeared after the end of the scenario. The same shape is in `DL8b.2.txt`, `DL8b.3.txt` and `DL8b.extra5..11.txt` (for example `DL8b.extra5.txt` [017]). The explanation, *inferred* (no log shows it): the actor consumed `PoisonPill` itself and stopped, so there was nothing to clean up, and the `Terminate()` that arrived later came from the guardian's `StopChild`. That build was replaced: `DL8` now stops with `InternalActorRef.stop()` (the `Terminate` is in the system queue before the gate opens) and `DL8c` has the actor stop itself; both give the inferred result in all three runs. `DL8b` keeps the `ActorSystem.stop` variant as a measured race: over 11 runs, 2 give `SuppressedDeadLetter(PoisonPill)` (`DL8b.1`, `extra4`) and 9 give no `PoisonPill` event and a `SuppressedDeadLetter(Terminate())` (`DL8b.2`, `DL8b.3`, `extra5..11`). An earlier set of the same 11 runs (before the `java.version` line was added to the harness; logs replaced by this set) gave 5 and 6: the split is not stable between sets. It does not contradict the inference; it shows, *inferred*, that "a stop accepted while `PoisonPill` is queued" only dead-letters the `PoisonPill` when `Terminate` is processed before the `PoisonPill` is dequeued.
2. **The recipient of `DL5` (a).** The wrapper `DeadLetter(SuppressedMsg, probe, some)` told to `deadLetters` publishes `recipient = dls`, not `some` (S4: the `DeadLetter` is unwrapped by `specialHandle(d.message, d.sender)`). The analysis said only "SuppressedDeadLetter for both"; the recipient was not predicted, and it is `dls`.

No other expectation differed.

## 6. Limits of this evidence

- One JVM per run, default dispatcher with `parallelism-max = 4`, Classic actors, local only; no remote, no cluster, no Typed. Java 1.8.0_504 only.
- Sends came from the main thread (not from an actor's `receive`), except `DL8c` (the stop is inside `receive`).
- `DL6` is one wrapper class (`W`, a user `WrappedMessage`), one nesting level, and the default `log-dead-letters = 10`; the stdout line was read for the control only (the `Info` collector shows the same event); `ActorSelection` as a wrapper (S1 of the spec) was not run beyond what the existing spec covers.
- `DL7` uses capacity 1 and timeout 0 (the `BoundedMailbox` branch `pushTimeOut.length >= 0`); the `UnboundedControlAwareMailbox`/deque/priority variants of `M` (`M:595-625`, `M:1031`) and a timeout greater than 0 were not run.
- `DL8`: one `m2` and one `PoisonPill` in the queue; the relative order of several `Kill`/`PoisonPill` dead letters at stop (item 5c of the amendment) was not run. `DL8b` is a race and is reported as one.
- `Terminated` (`DL3`) was told by hand from a helper in package `org.apache.pekko.actor` (its constructor is `private[pekko]`); that is not the path by which the runtime sends one.
- Option 1 is the spec as shipped; its two tests passed three times, and it contains no `PoisonPill`, no no-sender case and no bounded mailbox, so it is evidence only for the `SuppressedMsg`/`NormalMsg` rows.
- Timing: Option 1 took about 54 s by the sum of its three sbt `Total time` lines (42 s, 5 s, 7 s; the first run compiled the modules); Option 2 compiled in 3 s (`harness-compile.txt`) and the 41 JVM runs together took about 30 s of wall clock, as reported by the Dev (the rerun script started at 10:17:40 and finished at 10:18:12; no log shows those two times, only DL6's `10:17:54` stamp falls inside; a `DL8b` run that does not see the `Terminate()` waits 5 s).
- The first set of Option 2 logs (41 runs, same scenarios, harness without the `java.version` line) was replaced by this set so that the logs carry the Java version and exit codes. Observations of `DL1` to `DL8c` were the same in both sets; only the `DL8b` split changed (5/6 earlier, 2/9 now).
