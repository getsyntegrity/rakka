## 4. Findings and comparison with the code reading

- The full entry has the shape of P5/P6, for a real sender and without it; ` from ` is absent for `noSender` and for `deadLetters` (`LG1` [016], [025]) and for the `Dropped` of the spec (`sender=null`).
- The count is shared by `DeadLetter`, `Dropped` and `UnhandledMessage` (`LG5` [015], [024]); `Dropped` and `UnhandledMessage` lack the sentence "If this is not an expected behavior...".
- The suffix reads **`[5.000 min]`** and **`[2.000 s]`** (P4 predicted it); `of which 2 were not logged` is `count - maxCount - 1` = 7 - 4 - 1 (P3).
- `on` never suspends (`LG2`); `off` starts no listener (`LG3`); a finite limit with `infinite` stops the listener after the limit-th entry (`LG4`).
- Suppressed messages do not count and are not logged (`LG6`); this confirms `DL6`.
- With `during-shutdown` off, a dead letter produced after the start of `finalTerminate` is not logged; with `on` it is (`LG7` against `LG8`).
- A logger is an actor: a dead letter that it produces is a new event processed after the current entry, and the limit bounds the cycle (`LG9`).

None. P1 to P7 predicted each of these values.

## 6. Limits of this evidence

- Local, Classic `ActorSystem`, default dispatcher, one JVM per run, Java 1.8.0_504 only. The harness depends on `pekko-actor-typed` 1.7.1, which makes the default logger `Slf4jLogger` (a no-op without a provider); the harness sets `pekko.use-slf4j = off` so the default logger prints. The main instrument is `info recv` (the event stream); the stdout lines agree with it in every scenario: the raw count of `info recv` and of stdout `[INFO]` lines is the number of dead-letter Infos (marker `pekkoDeadLetter`) plus the one of the `CoordinatedShutdown` (section 3). That `pekko.use-slf4j = off` changes neither the content nor the count of the Info is **inferred** from the code reading (`L:139-147` publishes the Info straight to the event stream), not shown by a run with the setting left on.
- "No Info" is shown by the listener being idle and a fence, or by the listener's absence (`LG3`, `LG4`), not by a long wait.
- The suspension is a time deadline: the harness waits until 2.3 s after message 4 (`LG5` [050]); that wait is the scenario, not a synchronisation. Durations other than 2 s and 5 minutes, and `suspend-duration` in other units, were not run.
- The reset of the counter at `Int.MaxValue` (`L:55-63`), the `Dropped` with a real sender or recipient `deadLetters`, `UnhandledMessage` without sender, the nested `DeadLetter` and `WrappedMessage` texts of other wrappers were not run. The testkit WARNING of `TestEventListener` appears in the output of Option 1 and is not asserted here.
- In `LG7`/`LG8` the collectors are `/system` actors and the listener is polled from `PostStop` (`DlProbe`); only the default `during-shutdown` values `off` and `on` were run.
- The copy of Option 1 is the build of `git archive`; Option 2 used the published 1.7.1 jars. The duration of the 27 JVM runs was not measured.
