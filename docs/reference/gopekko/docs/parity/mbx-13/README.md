## What the Pekko source says about the two sentences of the issue

The ACT2 reconciliation of the issue says that Pekko's capacity "does not count admitted lane items" and that D3 and D8 are "goPekko decisions, not Pekko semantics". Two independent readings of `DeathWatch.scala:109-110` (Dev 2 and QA) found that `watchedActorTerminated` runs `self.tell(Terminated(...))`, an ordinary send to the actor's own mailbox, so a `Terminated` takes a slot of a bounded mailbox and is placed when the death notification is processed. Counting it (D3) and its placement (D8) are Pekko properties. What is a goPekko mechanism is the internal "lane" that carries them and the counting of Port posts (D6, whose principle is Pekko's: an answer from outside is a message to the `ActorRef`). The body of the issue has not been edited. The correction was posted as an append-only comment on #791 (https://github.com/getsyntegrity/gopekko/issues/791#issuecomment-6449811197); see O-5 in "Status of the remaining points".

### Architecture review correction (2026-10-27, after the decisions above)

An architecture review of the head `0d75e3be662fe8bd6ec994ae8a9b7c3f1a75e669` made two findings. This subsection records the current correction. It does **not** rewrite the Owner's decisions or their provenance: the words quoted above (O-1, O-2, D-1, D-2, D-5 and the authorizations) are unchanged, and so is the Owner's wording "the four Go-only rows". What is corrected is the classification that this README gave to the first of those rows. *Refined on 2026-10-28 by the Owner's last editorial message (above): the order of one producer's dead letters had been called a goPekko-specific guarantee because no Pekko spec asserts it; that is not a semantic difference and not a guarantee exclusive to Go, and it is reclassified below.*

**Finding 1: the oracle of concurrent admission.** The absence of an equivalent upstream test is not the absence of an applicable oracle. What the pinned source says (Apache Pekko v1.7.1, `9a54d1294c3ac7821bbed3c940769c3d5027d1ff`), read and not executed:

- `BoundedMailbox.MessageQueue extends LinkedBlockingQueue[Envelope](capacity)` (`Mailbox.scala:720-725`). `BoundedQueueBasedMessageQueue.enqueue` admits with `queue.offer(handle, pushTimeOut.length, pushTimeOut.unit)` and, when it returns false, tells a `DeadLetter` to the dead letters (`Mailbox.scala:557-568`). Every producer thread reaches it through `Mailbox.enqueue` (`Dispatcher.scala:72-74`, `Mailbox.scala:96`). So, under concurrent producers with a stopped consumer, the admission and the capacity accounting are those of a bounded, thread-safe JDK queue: at most `capacity` elements are admitted and the others are refused at once. That guarantee belongs to the JDK queue (the documented behavior of `LinkedBlockingQueue`; QA read `LinkedBlockingQueue.offer(e, timeout, unit)` in the JDK 21 source, which holds the put lock and returns false when the count equals the capacity and the timeout is spent: **read by QA, not executed**; that a Pekko run uses a JDK with the same contract is **assumed**).
- **Order of one producer's dead letters at a single local subscriber:** "Checked in Go and supported by a reading of the Pekko code for a single local subscriber; no differential execution." Read, not executed: the producer's thread tells the dead letters when the offer is refused (`Mailbox.scala:557-568`); `DeadLetterActorRef.!` calls `eventStream.publish` synchronously (`ActorRef.scala:736-743`); `EventStream` is a `SubchannelClassification` bus whose `publish` iterates the subscribers (`EventBus.scala:177-189`) and tells each with `subscriber ! event` (`EventStream.scala:51-54`). So one producer's dead letters reach one local subscriber in publication order, behind that subscriber's FIFO mailbox. No Pekko spec asserts it: that is a missing test, not a difference between Pekko and goPekko.
- What the Pekko tests cover: `MailboxConfigSpec.scala:142-192` runs producers and four consumers concurrently, but with capacity 10000 (never saturated) or blocking timeouts; its one saturated zero-timeout case (`:85-87`) has one producer awaited before the consumers start. **No existing Pekko test** saturates a zero-timeout bounded mailbox with concurrent producers.

Classification of row 1 (it replaces "Go-only"; the evidence classes are those used above). The Owner's words for the first part: "Propiedad compartida; oráculo Pekko aplicable; escenario diferencial pendiente (ADR 0033 D13)."

**Finding 2: the tests of one-time delivery.** `take(3)` read the prefix `[1, 2, 200]` and would also have accepted `[1, 2, 200, 200]`, leaving the duplicate in the channel. After the last expected delivery, each exactness scenario now reads a completion barrier: a sentinel message that the actor records only after everything admitted ahead of it, and the scenario fails on any delivery before it. It is applied to E2 (`TestBoundedMailboxUnwatchThenWatchWithDeliversTheNewMessageOnce`), to E1 (`TestBoundedMailboxWatchWithAfterADroppedPlainTerminatedDeliversThePlainTerminated`, both phases), to the two-notification test (both cases) and to the Port rejection test; no other test of the file claims exactness. A `Stop` is not a valid barrier: a `Terminated` still queued when the watcher stops is discarded without a dead letter (ADR 0030 P-3), so a duplicate would vanish. The sentinel is told only after the last expected delivery was read, because a pending death notification would be enqueued behind it (D8). The barrier detects surplus deliveries that were admitted before the sentinel; it does not detect an arbitrary delivery that arrives after it, which is acceptable here because every input of these scenarios is consumed before the sentinel is told (AO's reviewer noted the limit). No sleep, no polling and no time window is a witness; the 30 s bounds only end a failed wait. Gates are opened and actors stopped by a cleanup on every path. The check that the new assertions detect a duplicate is described in the evidence comment: a duplicate delivery was injected in a scratch copy, in the test actor only, outside the repository; the original assertions passed with it and the new ones failed. It is a controlled, reversible check, **not** a mutation campaign.
