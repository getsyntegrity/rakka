## 4. Carrier B: demonstration of the five items (by reading)

Proposal under test: the same-System release stays in `leaveWatchees` (`watch.go:407-413`, called at today's `stop.go:56`) and stays synchronous; the foreign release is a new last step of `acceptStop` (after `emit` and after `Execute(c.drain)`, see 4.6) that groups subjects by owner System and calls `owner.exec.Execute(closure)` once per owner. Closure: for each id, `rec := owner.lookupID(id); if rec != nil { rec.removeWatcher(wid) }`. It captures `(owner, ids, wid)`; `watchReg` gets an `owner *System` field; `takeOutgoingLocked` returns `(id, owner)` pairs inside the same `c.mu` section that sets `stopRequested` (`stop.go:44-55`).

### 4.1 Item (1): no `System.mu` / `cell.mu` held at the send, on all routes

**READ under E1-E10 (no counterexample found by reading; not executed, not implemented).** `acceptStop` is the only caller of `leaveWatchees`. At today's `stop.go:56`, `57` and `59` the lock set is {}: `closeGate` (`stop.go:43`, `hierarchy.go:174-178`) released before `c.mu.Lock()` (`stop.go:44`), and both exits of the critical section unlock before line 56 (`stop.go:46` returns early, `stop.go:55`). The designed foreign hand-off comes after those statements in the same function and acquires nothing before its `Execute`, so its lock set is {} on every route. Every route that reaches `acceptStop` has lock set {} at the call (table 2.1): `System.Stop`, `Context.Stop`, `StopSelf`, terminate cascade (`stop.go:83`), supervision stop decisions (`apply` `:331`, `applyRestart` `:188`, `stopRound` `:263`), restart failure paths (`restartFailed` `:497`, `reportInitFailure` `:534`, `faultCreate` `:293`, `failParent` `:343`), `receiveFailed` (`cell.go:340`), `startFailed` (`start_failure.go:174`), `terminatedFailed` (`watch.go:487`), port failure (`port.go:139`), spawn failure/stopping (`spawn.go:120`), guardian paths (`guardian.go:124`, `OnTerminated` via `StopSelf`), shutdown (`Terminate`). Routes `continueRestart`, `runPreRestart`, `runSys` bodies reach `acceptStop` only through the functions in the table (they contain no direct call).

Caveat that is NOT a lock issue: see 4.6 (position of the send relative to `Execute(c.drain)`).

### 4.2 Item (2): inline executors

**READ under E1-E10 (no counterexample found by reading; not executed, not implemented)** for locks and reentrancy; semantics of test executors stated.

- Inline `B.exec` (runs `f` on the caller's goroutine): the closure runs on W's `acceptStop` stack, lock set {}. Its body: `owner.lookupID` (S1: `System.mu` alone, released by defer) then `rec.removeWatcher` (C34: `cell.mu` alone). It calls no user code, no `Execute`, no `publish`, no `emit`, no `acceptStop`, no `notifyTerminated`. `rec` is a `record`; its only implementor is `*cell[T]` (F3), so `removeWatcher` is the `delete` of `watch.go:371`. Nesting depth added: 1 stack frame; no reentrancy possible into either System through the closure.
- What runs on whose stack under inline executors: if `W.acceptStop` is called from W's own drain, the closure runs inside W's activation goroutine; if called from the SUBJECT's finalize stack (W's `OnTerminated` runs inline there, X10, and calls `StopSelf`), the closure runs on S's finalize stack with S in state `closed`, `watchers == nil` (`stop.go:109-110`), no lock held (`stop.go:117`): `removeWatcher` is a no-op delete on a nil map (F8). No lock edge, no wait.
- `sup1InlineExec` (region `supervision_goside_internal_test.go:640-670` opened): when `inline` is set `Execute` releases its own mutex and then runs `f` on the caller's goroutine, "with no lock held by the caller"; otherwise it appends to a queue. `ctlExec` (`cell_internal_test.go:20-52`): `Execute` appends under its own mutex (`:28-32`), never runs inline; `RunOne`/`RunAll` pop under the mutex and run `f` on the test's goroutine after unlocking. Neither executor holds its internal mutex while running `f`, so neither can create a lock cycle with the closure. The reported `ctlExec` property stands: a closure queued on a `ctlExec` that the test does not drive is never run (retention, 4.5).
- Order under inline `B.exec` with the designed placement: the closure runs after `emit("stop-accepted")` and after `Execute(c.drain)` (today's `stop.go:57`, `59`), on the stack of W's `acceptStop` (see 4.6). If `A.exec` is also inline, W's whole termination has run before the closure.

### 4.3 Item (3): cleanup progresses while S is alive and busy / suspended / restarting

**READ under E1-E10 (no counterexample found by reading; not executed, not implemented).** The closure needs: `B.exec.Execute` (a new goroutine on the production executor, `executor.go:22`), `B.mu` (S1) and `S.mu` (C34). `S.mu` and `B.mu` are never held across user code, `Execute`, `publish`, `emit`, a channel operation or a wait (1.1, 1.2; F2). Every invocation of user code was located and has lock set {}: factory (`cell.go:253`; `supervision_restart.go:415`), `AttachPort` (`cell.go:254`), `PreStart` (`cell.go:285`; `supervision_restart.go:437`), `PostRestart` (`:434`), `Receive` (`cell.go:312`), `OnTerminated` (`watch.go:463`), `ReceivePort` (`port.go:114`), `PostStop` (`stop.go:160`; `supervision_restart.go:373`), `PreRestart` (`supervision_restart.go:321`), `SupervisorStrategy`/decider (`supervision_failure.go:265-271`), `ResumeWith` continuation (`start_failure.go:116`), `Config.Logger` (`supervision_logging.go`, under `protect`), `eventSink.Event` (`system.go:173`), dead-letter subscribers (`internal/deadletter/hub.go:69`), `Handle.ID()` of a user-supplied `Handle` (`registry.go:27`, `watch.go:119,122`, `hierarchy.go:279`; all called before any lock is taken). "Handler blocked in user code", "suspended" (`suspended > 0`, a counter), "restarting" (`restarting`, `waitDone`, flags) are states, not lock holders: `removeWatcher` does not consult them (`watch.go:369-373`), `lookupID` does not (`registry.go:31-35`). So nothing in the closure can block on S's handler or on a lock held across user code. The only blocking possibility is waiting for a mutex held by another goroutine in a pure critical section (bounded; no section waits on anything, F2) or for the executor to schedule `f`.

Comparison: carrier A needs S's activation to take a `sysq` item; `drain` does not take system items once `stopRequested` is set (`cell.go:120-122` precedes `takeSysLocked` at 138), holds them while `restarting` (`supervision_restart.go:61-63`), and cannot run while S's handler never returns. B is strictly better on this axis. Both A and B still depend on `B.exec` accepting and scheduling work (A calls `Execute(S.drain)` unless S is already scheduled, as `recreate` does, `supervision_restart.go:98-105`).

### 4.4 Item (4): during and after shutdown of A (watcher) and B (subject)

**READ under E1-E10 (no counterexample found by reading; not executed, not implemented).** The statements about A's shutdown below hold for the designed placement, with the consequence stated in 4.6: a release may be issued after W closed or after A's shutdown completed.

- A shuts down while S is alive: A's `terminate` cascade calls `acceptStop` on every W (F5); each issues its closures to `B.exec` as the last step of its `acceptStop`, which with a concurrent `A.exec` may be after W closed and after A's shutdown completed (4.6). The closure does not touch A. `S.watchers[W.id]` is removed by the closure (or by S's finalize). Notifications from S to W in the window are discarded under `W.mu` by `stopRequested || closed` (`watch.go:253`) or by `admitDeathLocked` (`watch.go:331`). Closures may be numerous (one `go f()` per `(W, owner)` pair): a goroutine burst, not a correctness issue.
- B shuts down while W is alive: `S.finalize` takes `watchers` and sets it to nil (`stop.go:104-111`, `watch.go:389-396`) and notifies W on `A.exec` (X10). Later stops of W produce closures that find either `lookupID(id) == nil` (non-guardian after retirement, F6) or a closed cell with nil `watchers`: no-op (F8).
- Closure submitted after B terminated: runs normally (`exec` is never closed, F4; `go f()` does not refuse, `executor.go:22`). It touches `B.byID` (guardians only remain) and a closed cell: no-op.
- Guardians: they stay in `byID`, `closed`, `watchers == nil`. A new `Watch` of a closed guardian: `addWatcher` returns false (`watch.go:359-361`) -> immediate `notifyTerminated` (`watch.go:179-181`).
- A `removeWatcher` on a closed cell: `delete` of a nil map, no panic (F8).

### 4.6 Required design change (placement) and the comparison with carrier A

**Required design change (placement).** If the foreign hand-off were issued inside `leaveWatchees` (today's `stop.go:56`), it would run BEFORE `emit("stop-accepted")` (`stop.go:57`) and BEFORE `c.sys.exec.Execute(c.drain)` (`stop.go:59`). If `B.exec.Execute` then panicked or blocked, or the closure panicked under an inline executor, W would have `stopRequested = true` and `scheduled = true` (set at `stop.go:49-53`) but its own drain would never be handed over: W would stay stop-requested and scheduled, never drained, never terminated, and its `Done` would never close. Today `leaveWatchees` cannot fail that way (`lookupID` and `removeWatcher` are infallible). Concrete executors in the repository that can block in `Execute`: `serialExec` does `e.q <- f` on a 65536-slot channel (`termination_stress_internal_test.go:168-181`; test only, it blocks when full); the production executor cannot.

The `need` flag is false when W is already scheduled; then no activation is handed over and the foreign hand-off is still issued.

**Goexit residual (concrete gap of a plain last-statement hand-off; class READ; closed in the design by the deferred hand-off, see below; not implemented).** No counterexample to cleanup correctness was found for rows 1, 4, 5, 6, 9, 10, 11 and 12. 1. **EXECUTED, class "language semantics of a toy program, NOT evidence about goPekko code":** a throwaway Go program outside the repository (go1.27.2), not stored in it, mimicked `acceptStop` (same-System release; emit; inline `Execute(c.drain)` running a hook; the foreign hand-off registered with `defer` after the locked section). Panic in the hook: the hand-off is issued, then the panic reaches the caller's `recover`. Panic in `emit` (event sink): hand-off issued. `Goexit` in `emit`: hand-off issued. It proves nothing about lock order.

The closure runs only `B.lookupID` and `S.removeWatcher` (two short locks, one at a time) and no user code, so running it during Goexit unwinding on an inline `B.exec` is as safe as in the normal path (rows of 4.5). `acceptStop` has no other `defer` today (`stop.go:42-61`). **Implementation constraint:** the `defer` must be registered so that no other `defer` added later runs after it; it must remain the last thing that runs.

**Lost ordering (consequence of the move).** Before the move the foreign release was handed off before W's own drain was handed over, so the hand-off happened before W's termination. With the designed placement that ordering is gone: with a concurrent `A.exec`, W's drain can run to `finalize`, `Done(W)` can close, and even A's shutdown can complete before the stopper goroutine reaches the foreign hand-off, so the release can arrive after W is closed. This is harmless for the cleanup (interleavings 7 and 8: `removeWatcher` on a closed or retired subject is a no-op; a notification from S to a closed W is discarded by `watch.go:253`). It changes what can be asserted. "After `acceptStop` returns" means that the release was handed off, not that it completed. A test must NOT assert that `S.watchers` has no entry for W at the moment `Done(W)` closes; it must assert absence only after the executor of S's System has run the closure (`ctlExec` `RunAll`) or after S finalized. Under an inline `A.exec`, W's whole termination (including PostStop) runs inside `Execute(c.drain)` before the release is issued.

This is a design decision, not a lock matter. The same placement applies to carrier A, which also has to call `B.exec.Execute(S.drain)` when S is idle.

**B weaker than A:** (i) Pekko fidelity: `Unwatch` is processed by the subject in message order in Pekko; B is not in S's order (unobservable here: `watchers` is a mutex-guarded map). (ii) A goroutine per `(W, owner)` pair on `go f()`, even when S is idle and not scheduled. **B stronger than A:** liveness (4.3): A waits for S's activation, which is not taken once S has accepted its stop (`cell.go:120-122`), is held while S restarts (`supervision_restart.go:61-63`), and is blocked while S's handler runs; B needs only `B.exec` plus two short locks. A needs a new `sysKind`, a `sysItem` payload and a `runSys` case (`supervision_restart.go:21-26, 28-33, 124-135`); B needs one closure. Neither needs a generation.

**Executor-level hazard shared by A and B (and already present today):** cross-System `Execute` now flows in both directions (S->W today at `watch.go:265`; W->S new). With an executor that runs `f` inline while holding an executor-internal lock, two such executors form an ABBA cycle. None in the repo does that (F3 test executors: `ctlExec`, `sup1InlineExec`, `qExec`, `holdExec` release before running `f`; `serialExec` runs on its own goroutine). It is assumption E3 below.

## 5. Assumptions

### 5.1 Executor assumptions (suitable for a design document)

- E1. **Delivery.** `Execute(f)` eventually causes `f` to run. For the release closure at-least-once is sufficient (idempotent); for activations (`drain`, `finalize`) exactly-once is required by the existing design (`scheduled` flag, "activations never overlap", `cell.go:114-115`). A dropped `f` loses the release until the subject finalizes.
- E2. **No refusal, no panic.** `Execute` does not panic, does not refuse work and does not recover panics of `f`; it returns after a bounded time. It must not block indefinitely, because the foreign `Execute` is called on the caller's goroutine (user handler, stop path). With the designed placement it is called after W's own hand-off (`Execute(c.drain)`), so a foreign executor that panics or blocks does not strand W; it can still delay or abort the remaining statements of the caller (see 4.6; the caller can also be aborted by a panic or by a Goexit under an inline `A.exec`, in which case a plain last-statement hand-off would be skipped; the deferred hand-off, Q5 direction accepted, covers it; not implemented).
- E3. **Inline permitted, reentrant.** `Execute(f)` may run `f` on the caller's goroutine before returning. If it does, it holds no executor-internal lock (or any lock) while running `f`, and `f` may call `Execute` again (on the same or another executor), including an executor of another System.
- E4. **Happens-before.** The call `Execute(f)` happens-before the start of `f` (the `go` statement gives this; a queue hand-off must too). The recheck argument in 4.5 row 2 uses it.
- E5. **No head-of-line coupling.** Running `f` must not depend on the completion of earlier-submitted functions that may block in user code. If it does (single-threaded executor), the liveness advantage of carrier B disappears and an unrelated blocked handler delays the release (and other actors' activations).
- E6. **Concurrency.** Functions may run concurrently on different goroutines unless the executor serialises them; the closure relies only on `System.mu` and `cell.mu`, not on serial execution.
- E7. **Lifetime.** A System's executor is fixed at `newSystem` and is never closed or replaced (`system.go:135,150-152`); it stays usable after the System terminated, for as long as any registration, handle or queued closure refers to the System.
- E8. **Ownership of work.** The executor of System X runs only work about X's cells. The proposed closure keeps this: it runs on `B.exec` and touches only B's registry and B's cells; `notifyTerminated` runs `W.drain` on `A.exec` (`watch.go:265`).
- E9. **Test executors.** `ctlExec` and `holdExec` deliberately violate (1) until driven; with them the link remains until the executor runs or S finalizes. This is a property of the seam.
- E10. **Production executor.** `goroutineExecutor` (`go f()`) satisfies 1-8 and is never inline.

### 5.2 User-code and structural assumptions

- U1. User handlers and hooks hold no runtime lock when they call into the package (true by construction: the locks are unexported and no callout is made under them, 1.1-1.3, 2.2, 2.3, 2.5); user locks held across a call to `Stop`/`Watch` are outside this analysis.
- U2. User code in `OnTerminated`, `PostStop`, subscribers and hooks may call any API of the package; every API function was found to take its locks alone or in the order `System.mu -> cell.mu`.
- U3. Dead-letter subscribers do not block and do not panic (`deadletter.go:35-39`, documented).
- U4. Test seam bodies and test doubles hold no runtime lock themselves; only their call sites were checked.
- U5. No runtime panics (nil dereference, index) inside a critical section that has a non-deferred unlock.
- U6. Handles are issued by this package (`ownedHandle` is unexported; a user type cannot satisfy it except by embedding a concrete in-package handle).
