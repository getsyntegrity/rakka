## 3. Ownership and cleanup (hypothetical: the current code applied to a foreign subject)

Today `resolve` rejects a foreign handle (`watch.go:119-120`), so no foreign link exists. The table shows what the current release paths would do **if the resolve check were relaxed** to accept a foreign handle. W = watcher cell in System A; S = subject cell in System B.

| Event | W keeps | S keeps | Released? |
|---|---|---|---|
| Watch live (hypothetical) | `watching[S.id]`, `watchGen` (`watch.go:217`) | `watchers[W.id]` (`watch.go:365`): B references A's cell | until a release event |
| S terminates | `watching` deleted at admission (`watch.go:334`); `termEntry` until taken | `takeWatchersLocked` empties it (`watch.go:394`) | both |
| W unwatches | `delete(watching)`, `delete(termEntry)` | `removeWatcher(W.id)` only if S is reached | yes, if the owner's record is looked up |
| W stops, after the recheck | `takeOutgoingLocked` clears all (`watch.go:384`) | `leaveWatchees` looks in A's registry, finds nothing (`watch.go:407-413`) | **NO, would occur**: `S.watchers[W.id]` would stay until S finalizes; B would retain A's cell, unbounded for a long-lived S |
| W stops before the recheck | the recheck removes it through the captured record (`watch.go:184-186`) | removed | yes |
| System A shuts down | each watcher goes through "W stops" | same leak per watcher | **NO, would occur** for foreign subjects that outlive it |
| System B shuts down | `watching` consumed as each actor finalizes | each cell clears its own `watchers` | yes; guardians stay in `byID` with `closed`, a later watch gets an immediate `Terminated` |
| Watch after S retired | `lookup` nil gives an immediate `Terminated` (`watch.go:179-181`; same-System test R9 for retirement between resolve and link: `registry_retention_internal_test.go:430-432`) | n/a | yes |

`removeWatcher` ignores the generation (`watch.go:369-373`); safe today because one watcher's register and unregister are serialized by its activation (not exercised across Systems). DTH-02 AC1 ("only the matching registration generation") would need a generation parameter.

Options for what a registration stores: (1) resolve through `owner().lookupID(h.ID())` at register and at each withdrawal; (2) store `owner *System` per registration (**chosen direction, Q3**); (3) store the subject record, which retains its cell until the registration ends. `owner()` is implemented only by `ref` (`ref.go:28`) and `idHandle` (`hierarchy.go:82`). A user struct that embeds the interface type `Ref` does **not** satisfy the unexported `ownedHandle`: the interface's method set has no `owner()` (compile-checked in a throwaway module outside the repository; no repository file). Only an in-package type that embeds the concrete `*ref[T]` or `idHandle` would satisfy it, and external code cannot forge one.

### 3.1 Eventual release for a foreign subject (Q3 decided); carrier B accepted as design on 2026-10-25 with the Q5 defer; same-System release unchanged

#### Required design change: placement of the foreign hand-offs

**Today's code** (no foreign hand-off exists): `acceptStop` calls `leaveWatchees` at `stop.go:56`, `emit("stop-accepted")` at `stop.go:57` and `c.sys.exec.Execute(c.drain)` at `stop.go:59`. If the foreign hand-off were placed in `leaveWatchees`, it would run before `emit` and before `Execute(c.drain)`; if the foreign `Execute` then panicked or blocked (or the closure panicked under an inline executor), W would have `stopRequested` set and `scheduled` true (`stop.go:49-53`) but its own drain would never be handed over: W would stay stop-requested and scheduled, never be drained and never terminate, and its `Done` would never close.

**Designed code** (not implemented): `acceptStop` runs `closeGate`; the `c.mu` section that sets `stopRequested` and takes the same-System IDs and the foreign `(id, owner)` pairs; `leaveWatchees` for the same-System IDs (synchronous, unchanged); `emit`; `Execute(c.drain)` when `need`; and **last**, unconditionally (not inside `if need`), the foreign release (called `releaseForeign` in the lock analysis), one `owner.exec.Execute(closure)` per owner, **registered with `defer` right after the `c.mu` section** (after the unlock at `stop.go:55`; the early return of a repeated stop at `stop.go:45-48` registers nothing). The closure captures the watcher ID by value, never W's cell. The same placement applies to carrier A. A foreign `Execute` that blocks still blocks the caller of `acceptStop`, but only after W's own work was handed over; this is why E2 (no panic, bounded return) is an assumption. With the `defer`, the hand-off is also issued if `emit` or `Execute(c.drain)` panics, or ends the goroutine with `runtime.Goexit` under an inline `A.exec` (see "Goexit residual" below).

**Lost ordering (consequence of the move).** Before the move the foreign release was handed off before W's own drain, so it happened before W's termination. In the designed code that ordering is gone: with a concurrent `A.exec`, W can finalize, `Done(W)` can close and even A's shutdown can complete before the stopper reaches the foreign release, so the release can arrive after W is closed. That is harmless for the cleanup (interleavings 7 and 8: `removeWatcher` on a closed or retired subject is a no-op, and a notification from S to a closed W is discarded, `watch.go:253`). It changes the guarantee and the tests: "after `acceptStop` returns" means that the release was **handed off**, not completed; a test must **not** assert that `S.watchers` has no entry for W at the moment `Done(W)` closes, and must assert absence only after the executor of S's System ran the closure (`ctlExec` `RunAll`) or after S finalized. Under an inline `A.exec`, W's whole termination runs inside `Execute(c.drain)` before the release is issued.

**Goexit residual: closed in the design by the deferred hand-off (Q5 direction accepted; not implemented).** Without the `defer`, under an inline `A.exec` with `need == true` (a caller that is not W's own activation: external `System.Stop`, the parent's `terminate` loop, `Terminate`), `Execute(c.drain)` runs W's start and termination on the stopper's goroutine. A `runtime.Goexit` in a user hook that runs there (factory or `PreStart` via `startActor`, `stop.go:80`; `PostStop`, `stop.go:101`) hands the continuation to a fresh `Execute` (`cell.go:257-261`, `stop.go:160-163`) while the goroutine unwinds through `acceptStop`, which has no `defer` (`stop.go:42-61`; `cell.go:216-219`): the foreign hand-off is never issued and the link stays until S finalizes (same bounded retention as the panic residual). It does not exist with the production executor for the `Execute(c.drain)` path (`executor.go:22`, a separate goroutine); a panic or Goexit of a user-supplied event sink in `emit` skips the hand-off with any executor (a test seam today). **Owner decision (2026-10-25, work thread, not in a GitHub comment): Q5 direction accepted.** The foreign hand-off is registered with `defer` right after the `c.mu` section (after the unlock at `stop.go:55`; the early return at `stop.go:45-48` registers nothing). It covers the panic and the Goexit case, still runs last and touches no cell state (compare `stop.go:155-158`, `cell.go:237-240`). It is a **design direction**: not implemented, its tests are defined (6.1 items 13-17) but not written and not executed. Facts, by class: **READ** the lock set at the deferred call is {} (the defer is registered after `c.mu.Unlock()`; `closeGate` (`stop.go:43`) has returned; callers hold no runtime lock at any of the 16 `acceptStop` sites, lock analysis 2.1; when the deferred call runs, at function exit or while a panic or Goexit unwinds, the frames below have already run their own deferred unlocks; assumption U5 is unchanged); the deferred call touches only captured values (owner, ids, `wid`), never W's cell; the closure runs only `B.lookupID` and `S.removeWatcher` (two short locks, one at a time) and no user code, so running it during Goexit unwinding on an inline `B.exec` is as safe as in the normal path (carrier B demonstration 4.5); `acceptStop` has no other `defer` today (`stop.go:42-61`). **Order preserved:** same-System `leaveWatchees` (synchronous, unchanged), then `emit`, then `Execute(c.drain)` if `need`, then the foreign hand-offs (now via `defer`, so also on panic or Goexit); on the normal path the order is identical to the one already designed. **Implementation constraint:** the `defer` must remain the last thing that runs in `acceptStop`; no other `defer` added later may run after it. **Production:** with `executor.go:22` (`go f()`) the `Execute(c.drain)` path cannot end the stopper's goroutine (W's activation runs on its own goroutine), so the `defer` changes nothing observable there on that path; it additionally covers a panic or Goexit of a user-supplied event sink in `emit` (a test seam: `eventSink` appears only in `system.go` and `lifecycle_internal_test.go`, grep) and any future inline use. **Executor assumptions (numbered; used by the demonstration).**

1. **E1 Delivery.** `Execute(f)` eventually causes `f` to run. For the release closure at-least-once suffices (idempotent); activations require exactly-once (existing design). A dropped `f` loses the release until the subject finalizes.
2. **E2 No refusal, no panic.** `Execute` does not panic, does not refuse work, does not recover panics of `f`, and returns after a bounded time; it must not block indefinitely. The foreign `Execute` is called after W's own hand-off (`Execute(c.drain)`), so a foreign executor that panics or blocks does not strand W; it can still delay or abort the remaining statements of the caller (a panic, or under an inline `A.exec` a Goexit, would skip the foreign hand-off; the deferred hand-off, Q5 direction accepted, covers it; not implemented).
3. **E3 Inline permitted, reentrant.** `Execute(f)` may run `f` on the caller's goroutine; if it does, it holds no executor-internal lock (or any lock) while running `f`, and `f` may call `Execute` again, including on another System's executor.
4. **E4 Happens-before.** The call `Execute(f)` happens-before the start of `f`.
5. **E5 No head-of-line coupling.** Running `f` does not depend on the completion of earlier functions that may block in user code. If it does (single-threaded executor), the liveness advantage of B disappears.
6. **E6 Concurrency.** Functions may run concurrently unless the executor serialises them; the closure relies only on `System.mu` and `cell.mu`.
7. **E7 Lifetime.** A System's executor is fixed at `newSystem` and never closed or replaced (`system.go:135, 150-152`); it stays usable after the System terminated.
8. **E8 Ownership of work.** The executor of System X runs only work about X's cells; the closure runs on `B.exec` and touches only B's registry and cells.
9. **E9 Test executors.** `ctlExec` and `holdExec` deliberately violate E1 until driven; with them the link remains until the executor runs or S finalizes (a property of the seam).
10. **E10 Production executor.** `goroutineExecutor` (`go f()`, `executor.go:22`) satisfies E1-E8 and is never inline.

User and structural assumptions U1-U6 are in the [carrier B demonstration](cross-system-watch-carrier-b-demonstration.md), section 5.2. Executors outside this repository are unknown.

## 5. Actor ID uniqueness across Systems

IDs come from one process-wide `idSeq` (`id.go:14-18`), used by `commit` (`hierarchy.go:149`) and `nextAskID` (`ask_endpoint.go:40`). Per-cell `watching`, `termEntry`, `watchers` and `Terminated.Who()` would hold IDs of both Systems, so a collision would give a false `ErrWatchConflict` or a merged registration. `System.Stop(h)` resolves by ID alone with no owner check (`stop.go:20-24`); `Done` looks the registry up before its owner check (`system.go:183-187`). No `_test.go` references `idSeq` or `nextID` (grep, verified). Two copies of the package in one binary would have two sequences but incompatible handle types (untested).
