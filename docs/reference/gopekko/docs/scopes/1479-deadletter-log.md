## Objective

As a Go actor application developer who sets `Config.Logger`, I see one INFO entry for each dead letter, with Pekko's text (message type, sender, recipient, running count and the "may have terminated unexpectedly" advice), bounded by a limit that I can set, so that a message lost to a stopped actor is visible without a subscriber. A suppressible message (`DeadLetterSuppression`, #871) is **not** logged. This delivers the missing half of sub-row C-10a (`ActorSystemSpec.scala:164-186`) and its test P2, the INFO half.

## Proposed Go API (for the Owner at G2)

The listener is an actor under `/system` subscribed to the event stream (D-1, revised), as in Pekko; goPekko has no logging bus, so the entry is written to `Config.Logger` (`kit-logger`, `pkg/logger`: `Logger.Info(msg string, args ...any)`, key-value attributes) from the listener's own goroutine. The new exported surface is configuration only (EXP-1 below):

```go
type Config struct {
    // ...existing fields...
    // LogDeadLetters is how many dead letters are logged before logging is suspended or stops (Pekko log-dead-letters).
    // 0 means 10 (Pekko's default); DeadLettersLogOff (-1) turns the log off; DeadLettersLogAll logs every one.
    LogDeadLetters int
    // LogDeadLettersSuspend is how long logging stays suspended after LogDeadLetters entries (Pekko
    // log-dead-letters-suspend-duration). 0 means 5 minutes (Pekko's default); a negative value means forever.
    // (slice 2; until then the behavior is "forever")
    LogDeadLettersSuspend time.Duration
    // LogDeadLettersDuringShutdown keeps the log on while the System terminates (Pekko log-dead-letters-during-shutdown,
    // default off). (slice 2)
    LogDeadLettersDuringShutdown bool
}

const (
    DeadLettersLogOff = -1          // Pekko: off
    DeadLettersLogAll = math.MaxInt // Pekko: on (Int.MaxValue)
)
```

A nil `Config.Logger` keeps the log silent (the existing rule of `Config`; Pekko's default logger prints to stdout, a documented divergence). The entry is written at Info with the text of `L:134-137` and the attributes `source` (the recipient, as Pekko's log source), `marker` (`pekkoDeadLetter`) and `messageClass` (`pekkoMessageClass`).

## Decisions of form (each with its Pekko citation; for the Owner at G2)

- **D-1 (decided: option A, Owner, 2026-11-11). Where the log runs.** Pekko: `DeadLetterListener` is an *actor*, started by the system when the limit is above 0 (`AS:1068-1069`: `systemActorOf(Props[DeadLetterListener](), "deadLetterListener")`), that subscribes itself to `DeadLetter`, `Dropped` and `UnhandledMessage` in `preStart` (`L:40-44`), receives them as mailbox messages (`L:65-118`) and writes an `Info` (`L:139-147`); its state (`count`, the receive variant) belongs to that one actor and needs no lock (`L:36-38`); it is stopped in `finalTerminate` unless `log-dead-letters-during-shutdown` is on (`AS:1112-1117`, the stop at `:1115`). **Is a call from `System.publish` equivalent in goPekko? No.** The stream of goPekko delivers by a `Tell` into the subscriber's mailbox and never blocks on a subscriber: the publisher returns while the subscriber is blocked (ADR 0038 D1, oracle EV6 [003], [006]; the doc of `Publish` in `eventstream.go`: "by a Tell into its mailbox (D1). It never blocks on a subscriber"). A call from `publish` would run the Logger on the goroutine of the `Tell` that failed, so a slow Logger would slow every sender that hits a stopped actor; a Logger that tells a dead actor would re-enter `publish` on the same stack (the entry nested inside the entry); and the state would need a mutex that Pekko's actor does not have. Blocking, ordering and reentrancy differ, so the equivalence cannot be shown. **Decided (option A): the listener is an actor subscribed with `Subscribe[DeadLetter, DeadLetter]`** (ADR 0038 D2: a `SuppressedDeadLetter` is another type and does not reach it), started at the end of `newSystem` when `Config.Logger` is set and the limit is not `DeadLettersLogOff` (Pekko starts it when the limit is above 0, `AS:1068`); its fields are the count and the state (always, max count; suspend and suspended in slice 2), it handles one `DeadLetter` per `Receive`, and it calls the Logger inside the same protection as the supervision log (a panic or `runtime.Goexit` of the Logger neither fails the actor nor stops the System). It needs the `System` for `DeadLetters()` (the real-sender test of `L:150-152`) and for the clock: `Context.System()` is in develop (#1545). **Precondition: it lives under `/system`, which goPekko cannot spawn into yet.** `System.spawnTarget` returns `/user` only (`hierarchy.go:22-25`), `guardianSet` keeps only the `/user` node (`guardian.go:110-115`, `:178`) and `eventstream_watch.go:15` says "goPekko has no /system actor (#1055)". [#1055](https://github.com/getsyntegrity/gopekko/issues/1055) (SYS-18, open) is the story that adds it, scoped apart in `docs/scopes/1055-system-guardian.md` (its own scope PR, in progress); its R3 (a `/system` actor finishes its PostStop only after every `/user` actor finished and before `WhenTerminated` closes) is the ordering that lets the listener see the dead letters of the user termination, as in Pekko. **Options considered:** A (**decided**) the actor under `/system`, after #1055 (the order: the oracle PR, #1055, slice 1, slice 2; the oracle can run in parallel with #1055); B (discarded) an actor spawned at `/user` level now, with a reserved name: it appears in the user's name table, stops before the user actors whose dead letters it should log and makes `log-dead-letters-during-shutdown` impossible to honor; C (discarded) the call from `publish` (the first version of this scope): not equivalent, by the argument above.
- **D-2. Configuration shape.** Pekko: HOCON keys `AS:441-453`. Recommended: three flat fields of `Config` and two constants (above), zero values meaning Pekko's defaults (10, 5 minutes, off), because every existing `Config` field is flat and zero-value-usable. The defaults are those of Pekko's `reference.conf`: `log-dead-letters = 10` (`RC:58`), `log-dead-letters-during-shutdown = off` (`RC:63`) and `log-dead-letters-suspend-duration = 5 minutes` (`RC:68`). Alternative: a `DeadLetterLog` struct field; one more type to export; not proposed.
- **D-3. Which variants are ported, and when.** All four of `L:65-71` (always, max count, suspend, suspended) in the end, because Pekko's default (10, 5 minutes) is the suspend variant and `DSS` is its executable contract. Slice 1 delivers always, off and max count (the variant for an infinite suspension); until slice 2 the Go default is therefore "10 entries, then silence for good", marked `TODO(LOG-suspend)` in the code and the README, a known and short-lived divergence. Slice 2 adds the finite suspension (the default) and `log-dead-letters-during-shutdown`, which needs the oracle O2.
- **D-4. Suppression (the rule asked by the Owner).** Pekko does two things: the listener never subscribes to `SuppressedDeadLetter` (`L:40-44`), and `isWrappedSuppressed` skips a `DeadLetter` that wraps a suppressible payload (`L:154-158`, `DL6`). Go reproduces the first by construction: the listener subscribes to the channel `DeadLetter` (D-1) and `System.publish` publishes a suppressible message as a `SuppressedDeadLetter` (`deadletter.go:76-79`), another type that ADR 0038 D2 does not deliver to a `DeadLetter` subscriber, so nothing suppressed is logged or counted by default. **Nested dead letters (declared divergence):** Pekko's listener also receives a `DeadLetter` whose message is itself a `DeadLetter` (it is an `AllDeadLetters`, `R:579`; `WrappedMessage.unwrap` peels it, `L:122`, and the text says `wrapped in [...]`, `L:124`). `publish` returns early for such an event before `Publish(s, dl)` (`deadletter.go:81-83`, `TODO(EVT-03-deadletter-cycle)`, the loop breaker of scope 870 D-3) and the stream never carries it, so the listener never receives it: `PORT-GAP(LOG-nested)`, tied to the same TODO. The second Pekko rule needs `WrappedMessage`, which Go does not have: `PORT-GAP(LOG-wrapped-suppressed)` (the same PORT-GAP that scope 871 D-10 named for `DL6`), and the ` wrapped in [<class>]` part of the text is `PORT-GAP(LOG-wrapped-text)`. Both are marked greppable in the code and the README.
- **D-5. The text.** Recommended: Pekko's sentence verbatim up to `unexpectedly. `, because the specs match on it (`ASS:174, 200`; `DSS:62`), and a last sentence adapted to the Go fields: `This logging can be turned off or adjusted with Config.LogDeadLetters and Config.LogDeadLettersDuringShutdown.` (Pekko names its HOCON keys, `L:144-145`, which do not exist here). Message class: `fmt` `%T` of the message (Pekko: `getClass.getName`, `L:123`). Sender: `Actor[<path>#<uid>]`, built from `PathOf` and `ActorPath.UID` as Pekko's `ActorRef.toString` does (`R:188-190`), when the sender is real (not `DeadLetters()`, `L:150-152`). **Recipient:** `DeadLetter.To` is an `ID` and `PathOf` returns no path for a handle built from an ID alone (`ref.go:121`), so the recipient is printed as its ID, not as a path: `PORT-GAP(LOG-recipient-path)`. The pattern of P2 (`from Actor[...]` and `not delivered`) does not need the recipient path. Pekko's log *source* is the recipient's **path** (`L:141`, and the oracle `DL6` shows `pekko://dls/user/victim`); here the `source` attribute carries the same text as the recipient in the sentence, the ID, not a path, which is the same `PORT-GAP(LOG-recipient-path)`. Alternative: resolve the path from a registry; the actor is already gone from `byID` when the dead letter is published to a stopped actor, so it cannot be done without carrying the path in `DeadLetter`, whose shape `DeadLetter{Msg, Sender, To ID}` is the one #896 delivered (`deadletter.go:26-30`); changing that public type is another decision.
- **D-6. Time.** Pekko reads `Deadline.now` (`L:101, 111`). Recommended: `Config.Clock.Now` (the System clock, #1129), which makes L5 deterministic without sleeping; this widens the documented use of `Clock` (it says the System calls `Now` only for `StartTime`, `Uptime` and the Ask deadline), so the doc of `Clock` is amended in the same PR. A custom clock without a monotonic reading is the caller's choice. Alternative: the `nanotime` test seam of `options`; not public, so the caller could not test with it.
