# Ciclos de dependencias del inventario: causa, clasificacion y resolucion

Fuente: `python3 -I tools/package/cycles.py` (grafo `depends_on` fila->fila; 783 filas). Resultado: 69 componentes fuertemente conexas (SCC) de mas de una fila (tamanos 47, 23, 11, 9, 7, 6, 6, 5, 5, 4 x5, 3 x14 y 2 x45 aprox.), mas un ciclo unico a nivel de spec en Classic (26 specs) y otro en Typed (20). Este documento explica cada ciclo y propone como ordenarlo; el plan resultante esta en `docs/unit-plan.md`. **No se editaron los TSV**: las "correcciones propuestas" las decide el coordinador/Owner.

Clasificacion usada: **I** dependencia de implementacion real; **V** solo de validacion/uso (el spec de A usa a B para probar, o B es consumidor de A); **C** de configuracion (la fila de claves depende del consumidor que las lee); **D** referencia documental mal expresada (el productor lista a su consumidor, o hermanos de un mismo comportamiento).

Principio de resolucion: (1) una dependencia **V**, **C** o **D** no ordena la implementacion: se retira del orden (y se propone retirarla del TSV); (2) un par de filas **I** mutuas son un solo comportamiento y entran en la **misma unidad** y el mismo PR/serie de PR; (3) si queda una dependencia **I** unidireccional hacia una unidad posterior, se define una **interfaz temporal** (seccion 3) con contrato minimo y se nombra la prueba de integracion que la reemplaza. Un doble no demuestra que el componente real cumpla: la fila consumidora queda `partial` hasta esa prueba.

## 3. Interfaces temporales (costuras)

Regla general: la unidad consumidora define el trait con el contrato minimo; se prueba con un doble que cumple las aserciones A# de la fila productora citadas; al llegar el productor se reemplaza el doble y se re-ejecutan **los mismos tests** mas la prueba de integracion nombrada. Ningun doble reduce el contrato de la fila productora. La fila consumidora queda `partial` hasta el reemplazo.

## 4. Validacion con dobles frente a integracion

- Con dobles se valida: el algoritmo propio de la fila (maquina de estados, orden, formato de mensajes de error) usando solo las aserciones que no cruzan la interfaz.
- Con integracion se valida: lo que cruza la costura (entrega real, suspension real, cartas muertas reales, extension real). Tabla de reemplazo en la seccion 3. Un test con doble nunca cuenta como `validation=done` de la fila consumidora.
- Criterio de reemplazo automatico: el PR de la unidad productora debe incluir el test de integracion y mover la fila consumidora de `partial` a su estado final si no queda `Q:` abierta.

## 5. Ciclos a nivel de spec

- **Classic (26 specs, un ciclo unico).** Es la proyeccion del grafo de filas: casi cada par de specs tiene una arista en ambos sentidos (UTIL, CFG, REF, MBX, DSP, EVT, CELL, SYS...). No se resuelve ordenando specs sino **repartiendo las filas por capas**. Camino de fundamentos a Classic completo: Ola 0 (UTIL/PATH puros) -> Ola 1 (HOCON, Settings, EventBus sin loggers, scheduler) -> Ola 2 (mailbox/dispatcher con `CellInvoke`, referencias, celda, supervision, restart/stop, watch) -> Ola 3 (sistema, proveedor, extensiones, ActorSelection) -> Ola 4 (ask, FSM, routers, logging completo) -> Ola 5 (CoordinatedShutdown, terminate, serializacion, IO) -> Ola 6 (testkit, superficie Java). Las aristas hacia adelante que persisten (153, Anexo de `docs/unit-plan.md`) son V/C/D o estan cubiertas por S1-S11.
- **Typed (20 specs, un ciclo unico).** BEH, SIG, SUP, CTX, ADP, STASH, TMR, EVT, LOG se referencian entre si. Se rompe separando *dato* (tipos de senal, Behavior, ActorRef: P48) de *comportamiento* (adaptador P49, sistema P50, observabilidad P52, interceptores/timers/stash P53, contexto P54, supervision P55). El camino a Typed e interoperabilidad: Classic completo (hasta P39 para sistema y terminacion; P22/P23 para ciclo de vida) -> P48 -> P49 (adaptador clasico) -> P50..P53 -> P54..P60 -> P61..P64 (javadsl y testkits). La interoperabilidad (ADP-002/005, SUP-020/021, EXT-002.3) se prueba en P55/P49 contra la celda clasica real, no contra doble. **Condicion:** Q-X-8 (a) "replicar capas" propuesta no aceptada; si el Owner elige (b) runtime nativo, P49 y P50 se rehacen y la interoperabilidad deja de ser un adaptador.
